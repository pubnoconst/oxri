## Context

Principia #9 (RATIONALE 090): development moves to WSL, the site is generated in WSL and tested on the host, and no unsigned executable is built for Windows. The lab was a Go program: on the host it would have been exactly the unsigned binary Windows Antimalware quarantined. RATIONALE 090 set the condition for replacing it: only after its numbers match on the same build.

## What changed

- **`cmd/lab/lab.mjs`: the lab as a Node script.** It measures as the Go lab did, and was written against its code rather than from memory:
  - the same flags; Chrome launched with chromedp's own flags, in its order; the seven domains chromedp enabled on every page; the same DevTools commands in the same order, with every field as the Go protocol code sent them (Chrome rejects the network emulation without the empty `urlPattern` and the false flags);
  - the same pauses: 3 s after load, 500 ms after a tap and after typing, the visibility poll every 5 ms, the scroll a screen at a time every 300 ms; the same injected collector, timeline and resource scripts, copied unchanged;
  - the same report, with Go's number formatting (fixed decimals, a value exactly between two rounded to the even one).
  - It speaks to Chrome over the DevTools pipe: no package, no build step, no open port. It needs Node 18 or later and a Chrome.
  - It is type-checked under the site's strict rules (`cmd/lab/tsconfig.json`). The Node APIs it uses are declared by hand in `cmd/lab/node.d.ts`, as the site's globals are in `assets/types/globals.d.ts`; `npm run typecheck` and `mage typecheck` cover it.
- **`internal/labsite`: the seeded site as its own package.** The Go lab serves it in its process; `cmd/labserver` serves it from its own.
- **`cmd/labserver`:** serves the seeded site on loopback and prints its address as its first line. It stops on Ctrl-C, on a POST to `/__lab/stop`, or when its input closes.
- **CI:** the performance job runs both labs, one after the other, and puts both tables in the summary.

Four things differ from the Go lab, each found on the way:

- **The lab waits until the seeded server answers.** The server prints its address as soon as it listens; between Windows and WSL a moment passes before a new port is reachable from the other side.
- **Closing Chrome cannot fail a measurement.** Chrome's own processes outlive it for a moment and hold files in its profile; on Windows they are ended with it, and the profile is removed with retries.
- **The server is ended with a request.** A closed pipe did not reliably cross from Windows into WSL; the server stayed up until it was killed.
- **The login step opens a folded-away form first** (`reveal`). On a site with passkeys the code field is behind "Or sign in with Password & Authenticator"; the Go lab cannot measure that page on production. The seeded site has no passkeys and is unchanged.

- `gofmt`, `go vet ./...`, `go test ./...` (16 packages, in WSL), `tsc` for the site and for the lab.
- **On the owner's machine** (host Chrome 158, the seeded site served from WSL): 3 runs × 4 pages at once in 42 s, budget met; `/` 1180 ms (1104–1484), `/book-i` 1052 ms (1004–1532), `/journals` 1324 ms (1172–1424), `/login` 956 ms (944–1196); CLS 0.000, 0.001, 0.000, 0.000; 68 kB per photo. The Go lab's figures on the same machine (RATIONALE 088) were `/journals` 1464 ms (1100–1512).
- **Beacon:** every page's report holds TTFB, LCP, INP and CLS.
- **From inside WSL:** a clone on the Linux side, the host's `node.exe` through the interop: the same result, the report written back to the Linux side.
- **Production, signed out, 2 runs:** `/` 1138 ms, `/book-i` 1282 ms, `/journals` 1590 ms (CLS 0.005), `/login` 1284 ms.

## The two labs on one build

CI's runner (four cores), the seeded site, 3 cold runs × 4 pages at once per pass. Median LCP in ms; CLS was identical in every run of every pass of all four jobs (168 runs): `/` 0.000, `/book-i` 0.001, `/journals` 0.008, `/login` 0.000.

| Job | Passes, in order | Median LCP, all pages |
|---|---|---|
| 1 | Go lab, then the script | Go 1164 / 1340 / 1584 / 1240 by page; script 948 / 1076 / 1224 / 900 |
| 2 | Go, script, script, Go | Go 1486 both passes; script 1084 both: **27% lower**, whichever ran first |
| 3 | Go over a port, script, Go over the pipe, script | Go over a port 1540 (25.4 CPU-s in the lab process); Go over the pipe 1490 (18.7 CPU-s); script 1246 and 1076 (11.7 and 10.8 CPU-s) |
| 4 | Script, script with a process burning one CPU-second at each page load, the same again, script | script 1214; with the burner 1322: **9% higher** |

(Job 3 and 4 ran on a throwaway branch, PR #93, closed unmerged.)

What follows:

- **Run order is not the cause.** The Go lab is as slow when it runs last (job 2).
- **The transport is not the cause.** Over the pipe the Go lab measures 1490 ms against 1540 over a port (job 3).
- **The lab's own CPU is part of the cause.** The Go lab process spends about twice the CPU of the script on the same twelve page loads, and a lab-side process that burns one CPU-second at each page load makes the script's pages 9% slower (job 4). The Go lab's work is spread through the whole load and is not the same shape as that burner; more of the same mechanism may account for the rest, which is not shown.
- **Numbers from different jobs differ by about 10% on their own** (the script measured 1084 in job 2 and 1214 in job 4). Only comparisons within one job hold, and in every job the Go lab was 20–30% slower.

## What this means

The condition in RATIONALE 090 is met where the metric is deterministic, and not met in timing on CI. So the Go lab stays, and CI runs both (the performance job takes about 2.5 minutes), until the owner decides. On a machine with cores to spare the two agree within run-to-run spread: there the script's figures fall inside the Go lab's recorded ones.
