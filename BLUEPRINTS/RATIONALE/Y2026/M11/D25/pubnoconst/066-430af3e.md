## Context

The owner asked to embed Bible verses, and to highlight phrases in them. The design changed four times in one session as the owner refined it:

1. **bible.com links, with highlights stored as character ranges.** The verse came from data inside bible.com's own page. The owner rejected it: highlight markup must not reach the database, and the approach was "not very idiomatic".
2. **A free Bible API, with the browser fetching and the server verifying.** The owner set two rules here: "Forget highlighting for now. Have server verify client fetched verse integrity at the server level when posted." They chose to store the reference plus the plain text.
3. **Share links from any provider.** The owner's rule: "No, absolutely no scraping. If the provider provides verses, only then client should generate a preview." This implementation used bible-api.com links.
4. **A dropdown instead of a link (shipped).** The owner asked: "A drop down menu… user selects scripture. Then user selects bible, then book\*/from\*/to/translation appears. Stars are a must. Then the client finds the YLT or KJV verses as a priority." In review they added: the dropdown arrow sat too close to the border, and the book list was too tall, so it needed a search.

The owner prefers word-for-word translations: Young's Literal Translation first, then the King James. bible-api.com has no YLT, so the provider is the Free Use Bible API (HelloAO). It is free, needs no key, has no rate limit, serves openly licensed translations, and provides one static JSON file per chapter.

No free provider serves the NIV or other licensed translations, and no site whose links people commonly share (bible.com, Bible Gateway) has an API. Both facts were checked during the session.

## What changed

- **Editor** (`views/editor/media.go`, `assets/js/scripture-picker.js`):
  - Media is a dropdown with Link or Scripture. Scripture → Bible shows four fields:
    - **Book\***: a combobox searching the 66 books (`gen`, `1co`, `jhn`).
    - **From\***: `12:3`.
    - **To**: `4`, in the same chapter.
    - **Translation**: "YLT, or KJV where missing" by default, or one of seven named translations.
  - The browser fetches the chapter, builds the text, and posts the text plus the translation it used.
  - Required fields carry a star, and `aria-required` on the field itself.
  - Red error text is kept for real mistakes; an empty required field gets a quiet prompt in the preview.
  - The dropdowns draw their own chevron (two `currentColor` gradients), inset from the border in both themes.
- **Provider** (`internal/verse`):
  - The curated translation list, and the 66 books generated from the provider's `books.json` (identical across the seven translations).
  - `ParseChoice` mirrors the browser's field checks.
  - `Assemble` is the one text rule: text pieces in order, footnote markers and headings dropped, white space normalised, no space before closing punctuation.
  - `Source.Verify` fetches the chapter (cached), rebuilds the text, and refuses a mismatch.
- **Domain** (`internal/domain/passage.go`):
  - `Passage` holds which verses, the reference, the version label and the text.
  - Fields must be plain: control characters, line breaks and angle brackets are refused.
- **Storage**:
  - `journals.passage`, a nullable JSON column added in schema v8 (an additive `ALTER TABLE`).
  - It counts against the quota (Go and SQL agree), and backups and the Make Room re-submit carry it.
  - The column list now lives in one constant, `journalColumns`.
  - The entry's required `media_url` becomes the provider's chapter address; readers never see it.
- **Display** (`views/passage`): the passage is drawn as a clipping with the tweet box's classes, BIBLE and the version on top, the reference below.
- **CSP**: `connect-src` adds `https://bible.helloao.org` only.

## Why

- The browser shows exactly what the provider serves, and the server stores only what it fetched itself. A forged or stale text cannot be saved, so the client is not trusted.
- Both sides follow one assembly rule, so an honest save always matches. Browser and server output were compared by SHA-256 on six passages across five translations (poetry, footnote markers, words of Jesus): all identical.
- The text is stored with the entry, not fetched at view time. Pages render without the provider, and the owner chose this.
- A search fits 66 books better than a native list on a small screen. The list stays in the page flow, a few rows tall.

## Verification

- `go vet`, `staticcheck` and `deadcode -test` are clean. One `staticcheck` finding was fixed: a raw U+202E in a test literal.
- All tests pass:
  - forged text, a translation without the passage and missing required fields are all refused, with nothing stored;
  - a valid save, the edit form refilling, an edit that does not re-fetch, and switching back to a link;
  - the v7 → v8 migration;
  - quota parity;
  - backup round trip.
- The strict JS type-check passes.
- Browser pass on the in-memory server, using real clicks and typing: Scripture → Bible → type `jo` → click John → 3:16 to 17 → the YLT passage appeared. It caught two bugs the scripted checks missed, both fixed:
  - a click on a book closed the list before choosing it (list items are now focusable);
  - premature red errors.
- Local runs used `TURSO_DATABASE_URL=:memory:`, so the remote database was not migrated before review.
