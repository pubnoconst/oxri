## Context

The owner saved an entry linking to a post on X. The catalog it led to showed X's old embed, and only a refresh showed the site's own card. The card is drawn from a stored snapshot (PR #56), and the snapshot was only fetched in the background, after a page had already drawn the post. The first view after a save therefore always got the embed.

## What changed

- **`tweet.Filler.Now(ctx, url)`**: if the link is a post on X with no stored snapshot (and not in failure back-off), it fetches the snapshot and stores it. It waits at most `saveWait` (4 s). On failure or timeout nothing changes.
- **`handleJournalCreate` / `handleJournalUpdate`** call it after the save and before the redirect.

## Why

The page right after saving is the one the author looks at, so it should show the entry as it will look. A short, bounded wait on the save, the one request that changes the entry, keeps reads from ever waiting on X.

## Verification

- `TestNowStoresTheSnapshotBeforeTheSaveReturns`: the snapshot is stored when `Now` returns, a link that is not a post on X never reaches X, a stored post is not fetched again, and a nil Filler is safe.
- `go vet`, `staticcheck`, `deadcode -test` and all tests pass.

## Not done

- The editor's live preview, before saving, still uses X's embed.
- A save after the Make Room flow goes back through the editor, so it is covered. Restoring a backup is not covered, and the background fetch fills those snapshots.
