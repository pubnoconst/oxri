## Context

The owner: "These CIs are getting time-expensive." The `performance` job took about 4.5 minutes, against about 30 s for tests and build, and ran three times per change:
1. on the code push;
2. on the rationale push a minute later;
3. on `main` after the merge.

## What changed

- **`concurrency`** with `cancel-in-progress`: a newer push to the same PR (or branch) cancels the run it supersedes.
- **The `performance` job runs only on `pull_request`.** After a merge, `main` holds the tree the PR already measured.
- **`cmd/lab -parallel N`** measures pages at once, each in its own browser. Shared state (the LCP targets) is guarded; results keep their order. CI uses `-parallel 4` and 3 runs (was serial, 5).
  - **Why fewer runs suffice:** layout shift, the only gate, is the same on every run (073–079), and timings are reported, not gated.
  - **Timings are not comparable** between parallel and serial runs, since the browsers share the CPU. `mage benchmark` stays serial, so its figures remain comparable over time.

## Evidence

The lab steps, run locally: 264 s → 74 s. The result was the same: CLS 0.000 on every page, every field report complete.
