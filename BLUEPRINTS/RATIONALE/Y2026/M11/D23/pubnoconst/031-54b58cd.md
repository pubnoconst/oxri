## Problem

Every password+TOTP sign-in, including correct ones, waited behind a mandatory 30-second server-side "confirmation cooldown" (`/login/confirm`, polled via `/auth/totp-status`). The idea was to hide success or failure until the wait ended, so the wait itself rate-limited guessing.

In practice it taxed the legitimate owner on every sign-in and bought little:
- The per-IP lockout (5 failures / 5 min, in memory) already capped one address at about 1 guess per minute.
- A per-IP wait does nothing against a botnet spreading guesses across many addresses.
- An attacker also needs the Argon2id password, not just a 6-digit code, and the owner normally uses passkeys anyway.
- The confirm page ran a full-page refraction ripple for 30 s, the single heaviest render in the app on phones.

The owner was also concerned that IP-based lockout would burden the database. It doesn't: the failure counters were always in memory. The only database write on this path is the TOTP replay watermark, once per **successful** sign-in.

## Decision: asymmetric cost

- **Success is instant.** A correct password and code create the session and redirect immediately.
- **Failures cost time**, checked in this order and **before any Argon2id work**, so a flood can't burn CPU either:
  1. **Global budget:** 30 failures within 10 minutes from all addresses pauses password+code sign-in until the oldest failure ages out. Passkeys never pass through this path, so the owner can't be locked out. This **reverses** the earlier README note "per-IP failed-attempt lockout (never global lockout)". The owner chose to add botnet protection, made safe by keeping passkeys outside the budget.
  2. **Per-IP lockout:** 5 failures in 5 minutes (unchanged).
  3. **Per-IP hold:** after the n-th recent failure the address waits 2 s, 4 s, 8 s, then 16 s before its next attempt is evaluated. This replaces the old "one pending confirmation per IP" slot, with the same effect: an attacker can't parallelise or speed up.
- **Why instant success is safe:** hiding the outcome only mattered while the wait was the rate limiter. Now the limiting comes from holds that apply only to failures. A successful attacker holds a session anyway, so learning it instantly tells them nothing extra.
- **No oracle between factors:** wrong password and wrong code return the same message and the same status. Both factors are always evaluated, and a wrong-password attempt never consumes the valid code's time step.
- **Replay stays separate:** a replayed code is not counted as a failure (no hold), as before.

## Shape of the code

- New `internal/auth/login.go`: the policy constants, `LoginTOTP`, the global budget (bounded to the newest 30 timestamps), and `LoginError{Err, RetryAfter}` with `RetryAfter(err)`. `AuthenticateTOTPForIP` now delegates to the same core, without the password factor.
- Removed from `auth.go`: `PendingTOTPVerification`, `StartTOTPVerification`, `PendingTOTPStatus`, `RedeemTOTPVerification`, `TOTPConfirmDelay`, `BindingCookieName`, and `ErrTOTPPending`/`ErrTOTPConfirming`. Removed the `TOTPConfirmPage` view, its inline SVG filter, and its CSS.
- `POST /login` handles failures inline: a plain message, `401` (wrong) or `429` (held, locked, paused), and a `Retry-After` header. Copy reads like "Incorrect password or code. You can try again in 2 seconds."
- Net change: about −390 lines.

## Verification

- `internal/auth/login_test.go` on a controllable clock covers:
  - instant success and single use;
  - the 2/4/8/16 s escalation, then lockout and recovery;
  - held attempts rejected even with correct credentials (proof they're rejected before evaluation);
  - identical results for wrong password and wrong code, with the code not consumed;
  - per-IP isolation;
  - the global budget pausing, sessions still working, and sign-in resuming.
- The route test covers the instant flow (401 + `Retry-After: 2` → 429 while held → 303 + session cookie) and 404s for the removed endpoints.
- Live smoke test against local config matched.
