## Request (owner)

A vacate-space path for when Book N grows enough to push storage past the 4.5 GB budget.

**Finding:** books were *outside* the budget. Usage summed only the `journals` table, and `SaveBook` never checked the quota, so a book could not trigger Make Room at all. (With the 128 KiB per-book cap this could not overflow storage in practice. The owner chose to count books and vacate anyway, for honesty and in case the cap is ever raised.)

## Decision

- **One honest usage number.** Usage is journals + books, each row costing `RowOverheadBytes` plus its UTF-8 text. `BookBytes()` in Go mirrors the SQL, and a test pins that the two agree.
- **Book saves are quota-checked in their write transaction**, as journal writes are. Only *growth* can be refused: a save that shrinks a book always succeeds, even over the limit, so the owner can never be locked out of trimming.
- **Reuse Make Room; don't add a second page.** An over-quota book save is held, and the owner goes to `/journals/vacate-space/`. Space can only be freed from journals, so the journal page is where it belongs. Once enough is free, the page posts the book back to `/book-N` (auto-resubmit, as for journal entries).
- **Books are never evicted.** Only journal bytes count as vacatable, and "space needed" is capped at what vacating journals can actually free.
- **Copy:** with a book waiting, the lead says "Storage is full" (not "Your journal archive is full"), the first metric is labelled with the book's title, and the button reads "Save Book II now".
- **Type safety:** the single held submission (`*PendingSubmission`) became a sealed interface, `db.PendingSave`, which is exactly `PendingJournal` or `PendingBook`.
  - A half-journal/half-book state cannot be represented.
  - The view describes the held save through one type switch.
  - Clearing is kind-aware: a successful journal write clears only a held *journal* save, and a book save clears only a hold for *that* book.
  - The pending code moved out of `quota.go` into its own `pending.go`.

## Verification

- **DB:**
  - a fresh store's usage equals the seeded books;
  - book growth past the limit is refused with the exact shortfall (150 B), and the book is unchanged;
  - "space needed" for the held book matches;
  - a journal write keeps the book hold;
  - after freeing space the book saves and the hold clears;
  - shrinking is allowed even with a 1-byte limit;
  - with no journals, nothing is vacatable.
- **Existing quota tests** now build their limits on top of the seeded books (`seededBookBytes`).
- **HTTP:** an over-quota `POST /book-ii` returns 303 to Make Room. The page shows the book's form posting to `/book-ii` with no journal fields. Auto-vacate evicts the draft, the page is ready to resubmit, and the book is saved.
- **Chrome, on a throwaway in-memory server** (limit 6,000 B). The real database was deliberately not used, because the local server connects to remote Turso and auto-vacate deletes entries. Two drafts were created, then 3.5 KB was saved into Book II. Make Room showed "1.7 KB needed" and a plan removing one draft. After clicking "Clear space automatically", the page saved Book II by itself and landed on `/book-ii`.
