## Problem

Found while verifying PR #32 (RATIONALE 033): `assets/favicon.png` was a 1254×1254 RGB PNG of **968,203 bytes**, downloaded by every first-time visitor for an icon the browser draws at 16–48 px. It was by far the heaviest request on any page.

## Decision

- Downscale to **96×96** (4,911 bytes, about 197× smaller). 96 px is the largest size a favicon is drawn at in practice: a 32 px tab icon on 3× displays, or 48 px on 2×.
- Resample with an **exact area-average (box) filter**: each output pixel is the coverage-weighted mean of the source pixels beneath it. At a ~13× reduction this keeps the monogram's thin serifs smooth, where nearest-neighbour or plain bilinear sampling would alias or drop them.
- It was done with a throwaway Go program using only the standard library (`image/png`). No image tooling was installed and no dependency was added.
- The full-size master stays in git history (before `62ebb3c`) for any future larger icons, such as an apple-touch-icon.
- No cache handling was needed: with content-hashed URLs (RATIONALE 033), the new bytes produce a new `?v=` hash, so any cached old copy is simply bypassed.

## Verification

- Visual check of the 96 px result: the "RI" monogram, serifs, frame and rounded corners are intact.
- `go test ./assets/ ./routes/` pass (the typed `assets.Favicon` handle is unchanged).
