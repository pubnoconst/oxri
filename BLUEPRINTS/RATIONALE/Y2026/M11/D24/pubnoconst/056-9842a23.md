## Context

The UI/UX review found the browser's `confirm()` was the one place a grey system dialog broke the site's look. The owner: "stop depending on browser confirm() for deletes. Use HTMX."

Four places used it:
- single entry delete (`data-confirm`);
- passkey removal (`data-confirm`);
- the catalog's batch "Delete selected", "Delete all" and "Unpublish all" (`journals-catalog.js`).

## Decision

- **`views/confirm`** is one typed component.
  - A `Prompt` has a question, a confirm label, danger styling, and a sealed `Target`:
    - `PostTo(url)` gives the prompt its own POST form;
    - `SubmitForm(id)` submits an existing form, such as the batch bar, which can't nest a form.
  - `Render` returns the inline fragment when HTMX asks (`HX-Request`), and otherwise a whole confirmation page, so the same link works without JavaScript. It sends `Vary: HX-Request` and `no-store`.
- **Triggers:**
  - Entry and passkey deletes are links (`<a href hx-get hx-target>`) to `GET …/delete`.
  - The batch buttons fetch `GET /journals/batch/confirm?action=…`, with the selected ids, through `hx-include`.
  - The prompt arrives in a `.confirm-slot` beside the control. It names the consequence and the count ("Delete 2 selected entries permanently?"), and for passkeys the name.
- **Closing without a round trip:**
  - "Keep" has `autofocus`, so a stray Enter never confirms.
  - Keep or Escape clears the slot in the browser (`navigation-feedback.js`) and returns focus to the control that asked.
  - Changing the batch selection closes a stale batch prompt.
  - The navigation loader ignores `hx-get` links.
- **The server enforces it:** the prompt's button sends `confirmed=1`, and the destructive POSTs require it (`confirm.Confirmed`).
  - Entry and passkey deletes without it are redirected to the question, and nothing is deleted.
  - Destructive batch actions without it get 400 "Confirm that first."
  - Publishing or unpublishing the selection still acts at once, since the opposite button undoes it.
- **Hardening:** passkey ids are `url.PathEscape`d wherever they enter a URL. A shared `parseIDs` keeps only positive integer ids from untrusted form values.
- **Styling:** `.confirm-inline` is a quiet frame where the confirm button carries the colour. It enters with an opacity and translate fade (none under reduced motion). The whole-page variant is centred.
- **HIG §8** records the rule: confirm in place, never with `confirm()`.

## Verification

- **New `TestDestructiveActionsAskFirst`:**
  - the catalog has no `data-confirm` and fetches the entry prompt with `hx-get`;
  - signed out, the prompt redirects to sign-in;
  - HTMX gets a fragment and a plain GET gets a page, both posting `confirmed=1`;
  - an unconfirmed delete is redirected and deletes nothing, while a confirmed one deletes;
  - the batch prompt counts the selection and submits `batch-form` with `action` and `confirmed`;
  - non-destructive batch actions have no prompt;
  - an unconfirmed `delete_all` gets 400, and a confirmed one empties the archive.
- **Existing tests updated to confirm:** the journal return-target test and the passkey delete test.
- **Chrome, on a throwaway in-memory server** with the test sign-in code:
  - the prompt appears in place with focus on Keep, and the page doesn't dim;
  - Keep and Escape both close it;
  - a confirmed delete removed exactly one entry;
  - the batch prompt said "Delete 2 selected entries", closed when the selection changed, then said "Delete 1 selected entry", and confirmed;
  - the no-JS page rendered.
- **Not tried in the browser:** passkey removal, since the test server has no passkey. It's covered by tests.
