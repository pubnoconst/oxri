## Context

This is step 1 of the modularity and type-safety plan agreed in review. The owner's principle: *"diligence can betray you, type system won't."* The plan's order:
1. Capabilities enforced by types (this entry).
2. Content-hashed asset URLs.
3. Typed route paths and form structs.
4. Split `routes` into feature packages plus `httpx`.
5. Split `db.Store` into narrow repositories.
6. JS `@ts-check` and ES modules.
7. CSS split by component.

## Problem

`domain.AdminCap` was well designed (minted only by `internal/auth` through a one-time `CapMinter`) but **decorative**:
- None of the database write methods asked for it.
- Admin handlers protected themselves with `if !requireAdminOrRedirect(w, r, authSvc) { return }`. Omitting that line in a new handler would compile, ship, and expose writes such as `DeleteAll`.

An audit found every existing admin handler correctly gated, so **no live vulnerability**. The risk was the next handler.

An earlier claim in review was wrong and is corrected here: the `Create`/`Update(JournalInput)` methods **did** validate (they parsed through the domain internally). They were a redundant second entry point, not a bypass.

## Decision

- **Writes demand the capability.** The 12 administrative writes take a `domain.AdminCap`: `SaveBook`, `CreateValidated`, `UpdateValidated`, `SetPublished`, `SetAllPublished`, `ToggleBookmark`, `Delete`, `DeleteAll`, `SavePasskey`, `DeletePasskey`, `AutoVacateBytes`, `SetPendingSubmission` (which now returns an error). `Create`/`Update(JournalInput)` are removed from production, leaving one write path. Tests keep test-only conveniences in `cap_test.go`.
- **Handlers can only get the capability from the adapter.** `adminHandler func(w, r, cap domain.AdminCap)` can be served only through `adminOnly` (session) or `freshAdminOnly` (5-minute step-up, with `denyAPI` and `denyToSettingsSignIn` responses). A handler that skips the check has no cap to pass to a write, so it **does not compile**. All 14 gated handlers were converted, and the compiler confirmed every write call sits inside one.
- **Where types can't reach, runtime and a test take over.** Go cannot forbid the zero value `domain.AdminCap{}`:
  - `requireCap` rejects it at runtime with `db.ErrUnauthorized`.
  - `TestPrivilegedCallSites` parses all non-test sources with `go/ast` and fails the build if the literal appears outside the authentication-failure returns (`internal/auth/auth.go`, `serverfns/auth.go`).
  - The `AdminCap` doc comment no longer claims the struct "prevents literal construction", which was untrue.
- **Deliberately uncapped writes**, documented in `internal/db/capability.go`:
  - `SaveLastTOTPStep` and `UpdatePasskeyCredential`: sign-in bookkeeping, made before any session can exist.
  - `RestoreSnapshot`: the offline operator tool already holds raw database credentials, so a cap would add nothing. It is pinned to `cmd/backup` by the same `go/ast` test.
  - `SetMaxStorageBytes`: startup configuration.

## Verification

- `TestAdminWritesRejectZeroCap`: every capped write refuses a zero cap and leaves journals, passkeys, books and the pending submission unchanged.
- `TestPrivilegedCallSites`: verified to fail on a planted forgery (both a zero-cap literal and an unauthorized `RestoreSnapshot` call, with exact positions), then pass once it was removed.
- `TestAdminRoutesRefuseAnonymous`: every admin GET redirects to `/login?next=…`, every admin POST gets 403, and the seeded journal is untouched.
- No user-visible change.
